## 0. 当前实现状态

- 本地 30 款经典酒库。
- 本地推荐：根据口味、强度、材料进行主推荐和备选推荐。
- Agent 对话入口：前端调用 `/api/agent/chat`。
- GPT 偏好解析：配置 `OPENAI_API_KEY` 后可用，未配置时降级到本地解析。
- 外部配方查证工具：已接入 OpenAI `web_search`，可返回 citation。
- Agent 标准返回结构：已包含主推荐、备选、信任标签、来源引用、会话 patch。
- 结果页展示：已支持信任标签、citation 链接、外部查证酒款的材料和步骤。
- 轻量会话状态：前端已可向 Agent 传 session，后端可返回 `sessionPatch`。

### 部分完成

- “一杯主推荐 + 两个备选”：后端结构已支持；前端结果页当前主要展示主推荐，备选切换体验还未完整做成。
- 外部查证：后端已接入主流程；前端已能展示 citation，但“查证中”的过程态和手动查证按钮还未完善。
- 外部灵感检索：后端已有工具和低置信度触发路径；实际效果依赖 API key 和模型返回质量，前端还没有专门的“灵感方向”展示样式。
- 会话记忆：已有当前会话结构和传递机制；偏好覆盖、否定、移除等合并规则还未完整实现。

### 未完成

- 本地语义匹配层：尚未实现 `CocktailSemanticProfile`、`semanticQuery`、`semanticScore`。
- 语义匹配标签：`语义匹配`、`灵感方向` 的产品展示尚未完整落地。
- 本地候选 semantic rerank：尚未实现。
- 长期用户偏好画像、账号体系、历史记录：未做。
- 完整工具注册表和 OpenAI Agents SDK：未做，当前仍是轻量函数式编排。

## 1. 产品目标

当前产品已经具备移动端鸡尾酒推荐、经典酒库、SVG 酒图、跟做页和分享页的基础闭环。下一阶段的重点不是单纯让 AI 多说话，而是让用户感到：

> 我随便说一句，它就能推荐一杯靠谱、好看、我真的能做的酒。

AI 酒保的定位是 **克制、可靠、有审美的线上酒保**。它需要听懂用户的口味、心情、场景和手边材料，再基于本地经典酒库、规则引擎和必要的外部查证，给出清晰、可执行、可信的推荐。

## 2. 核心产品原则

### 2.1 默认给一杯明确推荐

Agent 默认不应该像搜索结果一样一次列很多杯酒，而是给出一杯主推荐，并提供两个轻量备选。

推荐结构：

- 主推荐：酒名、酒图、酒保判断、推荐理由、已有材料、缺失材料、强度、难度、下一步动作。
- 备选酒：只展示酒名、口味标签和差异点。
- 用户可以切换备选，但默认让 Agent 替用户做一个明确选择。

产品感受：

> 它替我选好了，但我仍然有选择权。

### 2.2 信息不完整时先推荐，再优化

当用户只说“想喝清爽一点的”这类模糊需求时，Agent 不应立刻追问一堆问题。

推荐策略：

- 先给一杯大众安全、易执行的经典推荐。
- 在推荐后提供轻量优化入口。
- 只有在信息缺失会明显影响安全或推荐质量时，才追问一个关键问题。

示例动作：

- 更低酒精
- 更甜一点
- 看看我家材料能不能做
- 换一杯果味的

### 2.3 语气克制、有判断、有审美

Agent 不是普通客服，也不是过度拟人的聊天机器人。

语气要求：

- 温和、自然、明确。
- 有酒保判断，而不是泛泛罗列。
- 有一点生活方式审美，但不要油腻。
- 不装熟，不用夸张营销话术。
- 不鼓励快速饮酒、拼酒或过量饮酒。

推荐语气示例：

> 今晚我会给你一杯 Paloma。它有葡萄柚的明亮感，清爽、不太压人，也比 Margarita 更轻松。

避免语气：

> 亲爱的，让这杯微醺小甜心陪你开启浪漫夜晚吧。

## 3. Agent 回答结构

每次推荐回答建议分为 5 层：

1. **酒保判断**  
   一句话给出明确选择。

2. **推荐理由**  
   结合用户输入解释为什么适合，而不是只介绍酒本身。

3. **可执行信息**  
   展示已有材料、缺失材料、难度、需要时间和关键步骤。

4. **信任信息**  
   标注经典配方、经典结构 twist、外部查证、来源引用或不确定性。

5. **下一步动作**  
   提供“我来试试”“更低酒精”“换一杯”“查证配方”等按钮。

这套结构同时适用于对话气泡、推荐结果页和后续 Agent 工具返回。

## 4. 联网查证策略

联网查证的价值是建立可信感，但不能每次都查，否则会拖慢体验、增加成本，也会让产品显得过重。

### 4.1 应该触发联网查证的情况

- 用户问到本地酒库没有的酒。
- 用户明确提到“官方配方”“标准做法”“正宗吗”“IBA”等词。
- 用户点击“查证配方”。
- Agent 做经典 twist 前，需要确认母体酒的经典结构。
- 本地推荐置信度低，当前酒库找不到足够贴合用户感觉的酒。

### 4.2 不默认触发联网查证的情况

- 首页普通探索推荐。
- 已有本地经典酒库能很好覆盖的需求。
- 分享文案生成。
- SVG 酒图展示。
- 跟做页基础步骤展示。

### 4.3 查证结果展示方式

查证不应像论文引用一样打断用户，而应像高级酒单上的小标识。

推荐展示：

- `经典酒库`
- `已查证`
- `来源：IBA`
- `外部查证`
- `经典结构改编`
- `非官方配方`
- `待确认`

用户点开后再看来源详情和链接。

示例：

> 配方参考 IBA 经典做法，已根据新手跟做稍作表达简化。

如果是 twist：

> 这是基于 Tommy’s Margarita 的清爽长饮改编，不是 IBA 官方配方。

## 5. 本地酒库找不到时的处理

Agent 不能因为本地 30 款酒库没有某杯酒，就简单告诉用户“没有”。

### 5.1 用户点名某杯酒，但本地没有

流程：

1. 判断酒名是否存在于本地酒库。
2. 如果不存在，进入外部配方查证模式。
3. 优先查 IBA 或可信调酒来源。
4. 返回查到的配方、来源、可信度和可执行步骤。
5. 如果查不到可靠来源，明确说明不确定，并推荐相近经典酒替代。

示例：

> Paper Plane 不在当前内置酒单里。我帮你查了一下，它通常由波本、Aperol、Amaro Nonino 和柠檬汁等量组成。我可以按这个来源给你做跟做步骤。

展示标识：

- `外部查证`
- `来源：Difford's / IBA / 可信来源`
- `可信度：较高`
- `加入临时酒单`
- `我来试试`

### 5.2 用户描述的感觉，本地酒库不够贴合

除了点名酒款，还有一种情况是用户描述的风味或场景超出当前酒库覆盖范围。

示例：

- 想要烟熏感、咸味、适合冬天的。
- 想喝带茶感、低酒精、不要气泡的。
- 想要热饮，适合晚上看电影。
- 想要无酒精但有鸡尾酒仪式感的。

这时应进入 **外部灵感检索模式**。

返回方式：

- 1 个主推荐。
- 2 个备选。
- 说明为什么它们更贴合。
- 标注经典、现代经典、外部查证或来源待确认。
- 如果来源不够可靠，只作为灵感方向，不直接当标准配方。

## 6. 本地推荐置信度规则

当本地推荐置信度低时，Agent 可以触发外部灵感检索。

低置信度信号：

- 用户想要的关键风味标签，本地候选几乎没有覆盖。
- 用户想要烟熏、咸味、茶感、热饮、无酒精等当前酒库薄弱方向。
- 所有候选都缺少关键材料。
- 用户连续点击“换一杯”或明确说“都不太像”。
- 本地最高分候选与用户需求存在明显冲突，比如用户说“不苦”，但候选偏苦。

产品表达：

> 这个感觉当前酒单里没有特别贴合的。我可以帮你查一杯更接近“烟熏、咸味、冬天感”的经典或现代经典方向。

## 6.1 标签优先、语义补充、外部兜底

用户对“口味/感觉”的表达不应该被固定标签限制。Agent 的理解策略应分成三层：

1. **标签优先**  
   对高频、稳定、会影响排序和过滤的需求，优先映射到结构化标签或 taste profile。  
   例如：清爽、酸甜、不苦、低酒精、果味、草本、奶油、咖啡、气泡、烈度。

2. **语义补充**  
   对开放式、氛围型、低频表达，不强行要求提前建标签，而是保留为语义描述。  
   例如：雨天、冬天感、松弛、像甜品但不腻、海边夜晚、松木感、看电影时慢慢喝。

3. **外部兜底**  
   如果本地标签匹配和本地语义匹配都无法覆盖，再触发外部灵感检索或外部配方查证。

推荐决策：

```text
用户输入
↓
AI 解析为结构化标签 + 语义描述
↓
先用标签 / taste profile 做本地推荐
↓
标签命中高：直接本地推荐
↓
标签命中一般，但语义描述能在本地酒库找到相似酒：本地语义推荐
↓
本地语义也覆盖不足：外部灵感检索
```

产品表达上可以增加以下信任标签：

- `经典酒库`
- `语义匹配`
- `外部查证`
- `灵感方向`

这个策略可以避免无限扩展标签，同时让 Agent 能处理用户更自然的感觉表达。

## 7. AI 与规则的边界

为了保证产品可信，AI 不应该凭空发明配方。

职责分工：

- 本地经典酒库：负责稳定、可执行的标准配方。
- 推荐规则：负责匹配口味、材料、强度、难度和场景。
- LLM：负责理解用户、组织表达、解释推荐、生成轻量文案。
- 外部检索工具：负责查证本地没有或需要来源确认的配方。
- SVG 渲染：负责统一、可控的视觉表达。
- 安全规则：负责饮酒风险提醒和边界控制。

禁止行为：

- 把 twist 说成官方配方。
- 查不到来源时编造配方。
- 用“更容易醉”作为卖点。
- 鼓励过量饮酒、拼酒或快速饮酒。
- 向未成年人提供饮酒建议。

## 8. 下一阶段体验优先级

建议下一阶段优先做“可信推荐闭环”，而不是直接做复杂自主 Agent。

优先级：

1. 强化 Agent 对话结果，让它输出主推荐、备选、推荐理由和下一步动作。
2. 接入外部查证结果展示，包括来源标识和 citation 链接。
3. 增加本地未命中酒款的外部查证流程。
4. 增加本地低置信度时的外部灵感检索流程。
5. 在当前会话里轻量记住用户口味和材料，不急着做长期画像。

不建议下一阶段优先做：

- 完整长期用户画像。
- 账号体系。
- GraphRAG 或向量库。
- 完全原创鸡尾酒生成。
- 复杂多 Agent 协作。

## 9. 后续实施提示

实现时可以分成三步：

### 第一步：前端可见的 Agent 体验

- 扩展 `/api/agent/chat` 返回结构。
- 前端展示主推荐、两个备选、推荐理由、行动按钮。
- 结果页展示“经典酒库 / 外部查证 / 非官方 twist”等信任标签。

### 第二步：外部查证接入对话流

- 当酒名不在本地酒库时，调用外部配方检索。
- 当用户要求官方或标准配方时，调用外部查证。
- 返回来源引用，并在前端以轻量链接展示。

### 第三步：低置信度外部灵感检索

- 为本地推荐分数增加置信度判断。
- 当本地候选不贴合时，触发外部灵感检索。
- 明确区分“查证配方”和“灵感方向”。

## 10. 一句话总结

下一阶段的 Agent 目标不是让 AI 更像 AI，而是让它更像一个懂酒、懂分寸、懂审美的线上酒保：

> 本地会的直接答，不会的去查，查不到就诚实说不确定；默认替用户做一个明确选择，同时保留轻量调整空间。
